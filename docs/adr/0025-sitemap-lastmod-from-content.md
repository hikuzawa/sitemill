# ADR 0025: サイトマップの lastmod は、ページの中身が最後に変わった日にする

- ステータス: 採用（2026-09-17）
- 関連: ADR 0007（静的ビルド・デプロイ・計測）、ADR 0023（Search Console の取り込み）、
  ADR 0024（守りたい性質は公開する直前に確かめる）

## 背景

サイトマップの `lastmod` は、各ページの信頼シグナルの `updated_at` をそのまま使っていた。
サービスはここにビルドの時刻（japan-open-today）や巡回の時刻（akiya-atlas）を入れるので、
**2026-09-17 時点で japan-open-today は 891 件すべて、akiya-atlas は 6,421 件中 6,390 件の lastmod が「今日」**だった。

毎日全ページが「今日変わった」と申告していると、Google は lastmod を信用しなくなる。本当に変わった
ページを先にクロールしてもらう手がかりが消える。japan-open-today では登録されていないページの大半が
「検出 - インデックス未登録」（まだクロールされていない）で、クロールの優先度が効く段階にある。

`updated_at` の意味（信頼シグナルの「最終更新」）は変えない。利用者に見せる時刻と、検索エンジンに
申告する「中身が変わった日」は別のものとして扱う。

## 決定

### 1. ビルドのたびにページの指紋を取り、変わった日だけ lastmod を進める

- 指紋は `<main>` の中身から作る。信頼シグナル・ヘッダ・フッタは `<main>` の外にあるので入らない
  （両サービスで全ページを確かめた）
- `data-sitemill-volatile` を付けた要素は除く。**日付から決まる表示**（「9 月 17 日は開館」、週の帯、
  今日開いている施設の一覧、開いている件数）に付ける。事実ではなく、その日に描いた結果なので
- 項目（`li` `tr` `dt` `dd` `p` `div` `section` `article`）の単位で行に分け、並べ替えてから指紋にする。
  今日の状態で並びが変わる一覧に、印を付けなくて済む
- 指紋と日付は `data/state/lastmod.json` に残す。日次のパイプラインが `data/state` をコミットするので、
  次の実行に引き継がれる。サイトから消えたページは残さない
- 初めて見たページは `updated_at` の日付（今日より先にはしない）

記録を残すのは `sitemill build`（`cmd_build`）だけ。テストや調査で `SiteBuilder` を直接使うときは
状態を書かず、lastmod はこれまでどおり `updated_at` から作る。

### 2. 付け忘れは実行レポートの数で分かるようにする

ビルドの実行レポートに `lastmod_changed`（中身が変わって今日になった）・`lastmod_added`（初めて見た）・
`lastmod_kept`（前回の日付のまま）を出す。**導入の翌日以降も `lastmod_changed` がほぼ全ページなら、
日付で変わる表示に印が付いていない**。

## 実測

同じデータを 9/17 と 9/18 の 2 つの日付でビルドし、指紋が変わるページを数えた。

| サービス | 印なし | 印あり |
| --- | --- | --- |
| japan-open-today | 882 / 891（判定・週の帯・今日の一覧・件数） | **6 / 891** |
| akiya-atlas（コミット済みの写し） | 1 / 6,421（トップの「最終更新は…」） | —（テンプレートは触っていない） |

japan-open-today に残る 6 件は、日によって判定が「不明」と「確定」を行き来する施設。不明のときは
公式ページへの主導線と地図リンクの置き方が変わる。そこに印を付けると公式ページの URL の変更まで
見えなくなるので、付けない。1 日数ページの前後は許容する。

akiya-atlas の物件ページの「取得日時」は巡回の時刻ではなく記録の抽出日（9/10〜9/16 に分布）で、
内容が変わったときしか動かない。テンプレートを直さなくても、2 回目の実行から効く。

## 影響

- 導入した最初のビルドでは、全ページが「初めて見た」になり、`updated_at` の日付（多くは今日）になる。
  2 回目から、変わったページだけが進む
- `data/state/lastmod.json` がコミット対象に増える（japan-open-today で約 900 件、akiya-atlas で約 6,400 件）。
  日次の差分は変わったページの行だけ
- テンプレートや共通の部品を変えると、そのページの lastmod は一斉に進む。見た目が変わったのは事実なので正しい
- deploy-only の実行（データをコミットしない）で進んだ日付は引き継がれない。次の full の実行で、
  コミット済みの記録と比べて改めて進む

## 追記（2026-09-19）: 実測の取り方が間違っていた

上の「実測」は、**同じデータを 2 つの日付でビルド**して数えたものである。この形では、
**再取得のたびに動く表示（取得日時・最終取得）が見えない**。データが同じなら取得日時も同じなので、
差が出ないからである。

akiya-atlas はこの見立てのまま上げ、2 回目の日次で **972 ページが「変わった」**（実質 300 件）になり、
テンプレートの 9 か所に `data-sitemill-volatile` を足すことになった。上の表の「akiya-atlas 1 / 6,421」は
この取り方の結果で、当てにならない。

**正しい取り方は、日付を固定して実データを 2 日分入れ替える**（手順は
`docs/runbook/upgrade-0.5.2-to-0.6.0.md`）。同じコードで 2 日分の `data/` を突き合わせると、
「取得時刻の表示だけで変わったページ」が見える。

この取り方で japan-open-today を測った（9/17 と 9/19 のデータ、同じコード・同じ日付）。

| | 結果 |
| --- | --- |
| 共通のページ | 892 |
| 指紋が変わったページ | **6**（2 施設 × 3 言語） |
| 取得時刻の表示だけで変わったページ | **0** |

変わった 6 ページは、同じ本文から LLM が住所の引用を言い直したもの
（`香川県三豊市仁尾町仁尾乙273-1` → `香川県三豊市仁尾町仁尾乙273-1 父母ヶ浜海水浴場`）。
取得日時の表示は、volatile を付けた `.why` の中と `<main>` の外（フッタの信頼シグナル）にあるため、
指紋に入っていない。

## 追記（2026-09-19）: 値が同じなら言い回しを凍結する

同じ本文を読み直しても LLM は言い直す。値（決定的パーサが決めた数・日付）は同じなのに引用だけが
動くので、事実が変わっていないページの lastmod が進む。akiya-atlas では一晩で区分 4 件・要約 51 件、
japan-open-today では一晩で 3 施設の引用が動いた。

**値が同じなら、引用・見出しは前回のまま残す**（`sitemill.store.wording.freeze_wording`、v0.7.3）。
取得日時のような毎回動くのが正しい項目は、新しい方を採る。並びは長さが同じときだけ突き合わせる。

限界を 2 つ書いておく。

- **引用そのものが値になる項目（住所・電話などの文字列）は凍結できない**。言い直しは値の変化として
  入ってくるので、上の 6 ページはこの対処では止まらない
- 凍結は「事実が変わるまで前回の言い回しを使い続ける」ことなので、**引用の選び方を直したときは、
  値が動くまで新しい引用に入れ替わらない**。読み直しの道具（akiya-atlas の `subsidy-deadlines` など）で
  明示的に入れ替える

## 追記（2026-09-19）: 見た目を変えた回は、指紋を作り直して日付を据え置く

上の「影響」に「テンプレートや共通の部品を変えると、そのページの lastmod は一斉に進む。見た目が
変わったのは事実なので正しい」と書いたが、**これは取り消す**。実際には害のほうが大きい。

- akiya-atlas は「取得時刻に `data-sitemill-volatile` を付ける」だけの変更で、6,547 ページ中
  **5,717 ページの指紋が変わった**。表示は 1 文字も変えていない
- そのまま配置すると翌日の実行で全ページが「今日変わった」になり、lastmod を「中身が最後に
  変わった日」にした意味が消える。akiya-atlas は手順書（`operations.md` 3-6）に、台帳を手で
  作り直す手順を足して回避していた

**v0.7.4 から、エンジンが自動で作り直す。** 台帳にテンプレートの鍵（`layout_key`: サービスと
sitemill のテンプレート全ファイルの内容と、指紋の作り方の版 `FINGERPRINT_VERSION` のハッシュ）を
残し、**鍵が変わった回は指紋を作り直して日付を動かさない**（実行レポートの `build.lastmod_relearned`
と、ビルドの警告に出る）。鍵を持たない台帳（この仕組みより前のもの）は作り直さず、鍵を書き足すだけ。

**事実が変わったページまで据え置く**ことになるが、その変化は次の実行で拾える。全ページを「今日」に
するほうが失うものが大きい、という判断である（1 日遅れる vs 全ページの手がかりが消える）。

実データで確かめた（japan-open-today、892 ページ）。テンプレートに属性を 1 つ足した回は
`lastmod_relearned` が 843 で `lastmod_changed` が 0、日付の分布は変更前と同じだった。次の回からは
これまでどおり中身の変化だけで進む。

## 追記（2026-09-21）: 作り直しを本番で確認した

japan-open-today がテンプレートを全面的に書き換えた（ADR 0013 の案B）翌日の日次:

| | 結果 |
| --- | --- |
| `lastmod_relearned` | 891（全ページ） |
| `lastmod_changed` | 0 |
| 台帳の日付の分布 | 前日と同一（9/18 が 867、9/19 が 18、9/20 が 6） |
| 本番のサイトマップ | 同じ分布 |

台帳の鍵だけが入れ替わり、**手作業は 1 つも要らなかった**。
