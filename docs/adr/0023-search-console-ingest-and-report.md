# ADR 0023: Search Console の取り込みと集計

- ステータス: 採用（2026-09-14）
- 関連: ADR 0014（自動改善ループ）の計測側。第 2 段階（LLM による改修の提案・適用）は
  ADR 0014 §6 の着手条件を満たすまで作らない
- 関連: ADR 0007（静的ビルド・デプロイ・計測）

## 背景

公開したサイトが検索から見つかっているかは、いまのところ人が Search Console の画面を開かないと
分からない。2 サービス（akiya-atlas・japan-open-today）に増え、今後も増えるので、**数字の取り込みと
集計はエンジン側に置く**。

特に公開直後は「何ページ送って、何ページ登録されたか」が一番知りたい数字で、これが見えないと
長期戦の見通しが立たない。

## 決定

### 1. 3 つの API を使う。取るだけで、Search Console 側は変えない

スコープは `webmasters.readonly` だけを要求する。

| API | 何が取れるか | 頻度 |
|---|---|---|
| `searchAnalytics/query` | 検索語・ページ・表示・クリック・CTR・平均掲載順位 | 日次 |
| `sitemaps` | 送信したサイトマップの状態（送信 URL 数・最終取得・エラー） | 日次 |
| `urlInspection/index:inspect` | 1 URL のインデックス状態 | 日次に一定件数ずつ |

認証はサービスアカウント。鍵は `.env` の `GOOGLE_SEARCH_CONSOLE_KEY`（JSON を base64 にした 1 行）
だけから読む。Search Console 側の権限は「制限付き」で足りる（実測で確認）。

### 2. 日付ごとに上書きする

Search Console の数字は **2〜3 日遅れて確定する**。毎日「直近 5 日」を取り直し、同じ日の行は
新しいもので置き換える。追記だと、確定前の数字が残って二重になる。

置き場所（サービスの `data/search/`、コミットする）:

```
performance/query/<YYYY-MM>.jsonl        日 × 検索語
performance/page/<YYYY-MM>.jsonl         日 × ページ
performance/page_query/<YYYY-MM>.jsonl   日 × ページ × 検索語
index/urls.json                          URL 検査の結果（URL ごとに最後の 1 回）
index/sitemaps.json                      サイトマップの状態
```

行数の上限に当たったら「打ち切られた」と記録する。**0 件と取りきれていないを混ぜない**。

### 3. インデックス数は URL 検査で数える。`sitemaps` の `indexed` は読まない

`sitemaps` API は `contents[].indexed` を返すが、Google はこの値を更新しておらず**常に 0** である。
これをインデックス数として出すと「889 ページ送って 0 ページ登録」という嘘になる。

代わりに URL 検査を**順に回す**。1 日の件数を決め（既定 200 件。Google の割り当ては 1 プロパティ
2,000 件/日）、未検査の URL を先に、次に検査した日が古い順に回す。891 ページなら 5 日で一巡する。

報告には「**検査した N ページのうち M ページが登録済み**」と、サイト全体のどれだけを検査したかを
併記する。数えていない分を「登録されていない」と読ませない。

サイトマップの送信数は「Google が最後に取得したサイトマップの中身」なので、ページを増やした
直後はサイトの URL 数とずれる。ずれているときは「再取得待ち」と書く。

### 4. 集計は 4 つ＋インデックス

1. **インデックスの進み具合**（先頭に置く。公開直後に一番知りたい）
2. 表示が多いのに CTR が低いページ（表示 30 以上・CTR 2% 未満）
3. 順位が落ちたページ（前の期間と比べて平均掲載順位が 3 以上悪化）
4. 新しく表示され始めたページ
5. まだ表示されていないページ（サイトマップにあるのに表示 0）

しきい値は定数にしてコードに置く（サービスごとに変えたくなったら設定へ移す）。

### 5. データが 0 でも読める形にする

公開直後は 0 が続く。そのとき「まだ表示回数がありません」と、いつから数えているかを出す。
**数字が無いことと、集計が壊れていることを混ぜない。**

### 6. 依存を 1 つ増やす（`google-auth`）

サービスアカウントの JWT 署名にだけ使う。トークンの交換と API 呼び出しは既存の httpx で行い、
`google-auth` の transport（requests を要求する）は使わない。RS256 の署名を自前で書くより、
鍵の扱いを枯れた実装に任せる方が安全と判断した。

## 影響

- サービス側は `sitemill search fetch` を日次に、`sitemill search report` を週次に足すだけ
- `site.toml` の `[search_console]` は省略できる（`base_url` のホストから `sc-domain:` を組み立てる）。
  URL プレフィックスのプロパティを使うサービスは `property` を明示する
- 取り込みは 1 日あたり数リクエスト＋URL 検査の件数。相手は Google の API だけで、
  巡回先のサイトには触れない
- 第 2 段階（LLM が「この検索語で表示されているのに CTR が低いから見出しを直す」と提案する）は
  この記録が貯まってから。ADR 0014 の許可リストと eval の歯止めをそのまま使う
