# 0015. 変化の少ないサイトは巡回間隔を延ばす（下限は週 1 回）

状態: 採用・実装済み（2026-09-12）。ADR 0003（礼儀正しい巡回）への追記にあたる。

## 背景

全国 270 の自治体サイトを毎晩そのまま取りに行っていた。1 日の実測では、変化があったのは
270 のうち 4〜46 サイト（1.5〜17%）で、残りは前日と同じ内容だった。相手は自治体の公開サーバで、
こちらの都合で毎晩叩き続ける理由がない。事業としても、負荷を理由に断られる方が損失が大きい。

一方で間隔を空けすぎると新規掲載に気づくのが遅れる。「気づくまでの遅れ」と「相手への負荷」は
そのまま交換関係にあるので、**どこまで遅れてよいか**を先に決める。

## 決定

そのサイトが最後に変化してからの日数で、次に取りに行くまでの間隔を決める。

| 最後の変化から | 間隔 | 新規掲載に気づく遅れ（最大） |
| --- | --- | --- |
| 7 日未満 | 毎日 | 1 日 |
| 7〜28 日 | 3 日ごと | 3 日 |
| 28 日以上 | 7 日ごと | 7 日 |

- **下限は週 1 回**。どれだけ動きが無くても、7 日に 1 度は必ず取りに行く。閉鎖・移転・様式変更に
  気づけなくなるため。
- **変化を見つけたら翌日から毎日に戻す**。動き出したサイトを取りこぼさない。
- **まだ取ったことがない source と、前回エラーだった source は常に取りに行く**。
- `--force`（`sitemill crawl --force`）は間隔を無視する。手元での再取得や、様式変更の追従に使う。
- 判定は source 単位（≒ホスト単位）で行う。1 つの source の中の個別ページは従来どおり
  条件付き GET（ETag / If-Modified-Since）で無駄な転送を避ける。

設定は `site.toml` の `[crawl]`（`adaptive_interval`、`fresh_days`、`slow_after_days`、
`mid_interval_days`、`max_interval_days`）。既定で有効。

## 根拠と見込み

- 1 日あたりの変化率を p とすると、7 日間変化しない割合は (1-p)^7。実測の p = 5%/日 なら約 70%、
  p = 15%/日 なら約 32% が 3 日間隔以上に落ちる。28 日で見ると p = 5% で約 24% が週 1 回になる。
- 定常状態では取得は 1 日あたり 270 → 120〜160 サイト程度に下がる見込み（実測は週次まとめで確認する）。
- 導入直後は全サイトの `changed_at` が同じ日に寄っているため（全国バックフィルの直後）、
  しばらくは全サイトが「毎日」のままになる。効き始めるのは変化が分散してから。

## 代替案と却下の理由

- **一律に週 1 回**: 負荷は最小になるが、更新の多い自治体（毎週入れ替わる一覧）で 1 週間遅れる。却下。
- **robots.txt の Crawl-delay だけに従う**: 1 回の取得間隔は守れても、毎日全件という頻度は減らない。却下。
- **サイトの更新履歴（RSS・sitemap の lastmod）を見る**: 使える自治体が少なく、無いサイトのために
  結局この仕組みが要る。将来、lastmod があるサイトで間隔をさらに詰める余地はある。
- **変化率を学習して最適化する**: 効果に対して複雑すぎる。3 段階で足りる（ADR 0014 の自動改善ループの
  対象にはなり得る）。
