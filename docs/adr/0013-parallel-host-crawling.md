# ADR 0013: ホスト単位の並列巡回・発見（提案）

- ステータス: 採用・実装済み（2026-09-10）。全国展開（akiya-atlas ADR 0008）の前提。
  実装: `fetch/client.py`（ホスト別 RLock）、`commands.py`（crawl / extract の source 単位プール、
  `crawl.max_workers` と `--workers`）、akiya-atlas `expand.run_discovery`（市町村単位プール）。

## 背景
現在の `PoliteClient` と発見・巡回は同期・逐次で、1 ホストにつき一定間隔（既定 3 秒 + jitter、
robots.txt の Crawl-delay 尊重）を空けて取得する（ADR 0003）。長野県 72 件の発見で約 21 分。
全国 1,741 市町村では逐次だと数時間かかる。礼儀（1 ホストあたりの間隔）は絶対に崩さずに、
別ホストへのアクセスを並行させて所要時間を短くしたい。

## 決定（設計）
politeness は**ホスト単位**の制約なので、**ホストが異なるリクエストは並行してよい**。
これを 2 段構えで実現する。今回は設計のみ、コードは書かない。

### 1. スレッドセーフな `PoliteClient`（sitemill エンジン）
現状の要となる不変条件は「同一ホストへの連続アクセスは delay 以上空ける」。`_wait_turn` が
`_last_request[host]` を読み書きしてこれを守っているが、スレッドセーフではない。次の最小変更で
並行化する:
- **ホスト別ロック**: `dict[str, threading.Lock]`（生成は master ロックで保護）。`get()` は
  対象ホストのロックを取ってから `_wait_turn` → リクエスト → 解放する。これで
  (a) 同一ホストは同時に 1 リクエストだけ、(b) delay はロック保持中に enforce され、
  (c) 別ホストは並行、が同時に成り立つ。
- **共有状態の保護**: `_last_request` と `request_count` はロック下で更新（`request_count` は
  専用ロックか `itertools.count`）。`httpx.Client`（同期）はスレッド間の並行 GET に耐える。
- **robots キャッシュ**: `RobotsCache` を共有し、二重取得を避けるためホスト初回だけ取得する
  ように取得部をホストロックで直列化する。
- 既定の挙動（`sleep`/`clock` 注入、jitter、Crawl-delay 尊重）は変えない。単一スレッドで使えば
  今と完全に同じ。

### 2. ホスト分割ワーカープール（オーケストレーション）
発見・巡回の対象を**ホスト単位のタスク**に分割し、`concurrent.futures.ThreadPoolExecutor`
（既定 `max_workers=8`、設定可能）に投入する。
- **発見**: 市町村 ≒ 別ホスト。市町村ごとに 1 タスク。
- **巡回**: source ≒ 別ホスト集合。source ごとに 1 タスク（`crawl_source` はそのまま使える）。
- 同一ホストを持つタスクはホストロックで自然に直列化される（稀）。総同時数は `max_workers` と
  ホストロックで二重に上限。
- グローバルな最大同時ホスト数を設定（例 8）。相手サーバー負荷を抑え、良き netizen を保つ。

### 3. 抽出（LLM）の並列化は別軸
抽出はネットワーク先が Anthropic API で、ページ間は独立。巡回とは別に、`max_workers`（API の
レート制限に合わせて 4〜8 程度）で並列化するか、Batch API を使う。巡回の並列化とは独立に効く。

### 4. CI マトリクス（代替・併用）
エンジンを変えずに並列化する道として、GitHub Actions の matrix で**都道府県ごとに 1 ジョブ**を
流す（47 並列）。別都道府県＝別ホスト群なので自然に並行し、politeness は各ジョブ内で保たれる。
ジョブは自分の都道府県ぶんの `data/sources/{slug}-auto.yaml` と `data/records/` だけを書き、
別コミット（または成果物集約ジョブ）でまとめる。無料枠の分数と後段のマージ調整が要点。

## 使い分け（推奨）
GitHub Actions は**ジョブごとの wall-clock 分を合算課金**する（matrix の並列ジョブでも合計分は減らない）。
private の無料枠は月 2,000 分。これを踏まえた使い分け（詳細は akiya-atlas ADR 0008）:
- **日次の増分更新**: エンジンのホストプール（Option 1+2）による**単一ジョブ**。1 ジョブの wall-clock を
  縮めるので課金分が減る。実測（2026-09-10、akiya-atlas 135 市町村・巡回 12 source・94 リクエスト）:
  crawl は逐次 4 分 26 秒 → 並列 8 で 1 分 55 秒（最長 1 source ≒ 30 ページ×3.5 秒に律速）、
  crawl→extract→heal→build のフル run は並列 8 で 1 分 59 秒。全国（巡回対象 約 150 source・
  約 1,260 リクエスト/日）に外挿すると逐次 約 60 分/日（月 約 1,900 分で枠ぎりぎり）、並列 8 で
  8〜10 分/日、build と Actions の準備を足しても 12〜15 分/日（月 360〜450 分）。
  matrix は課金分が 47 ジョブ分に膨らむため**日次には使わない**。
- **全国初回バックフィル**: 一度きりで数百〜千分規模になり無料枠を圧迫し、長時間ジョブは 6 時間上限にも
  弱い。**ローカル PC または Raspberry Pi で実行**して Actions 枠を使わないのを既定とする。クラウドで
  回す場合はホストプールの単一ジョブ（wall-clock 最小＝課金最小）にし、matrix は避ける。
- matrix（Option 4）は wall-clock を縮めたい**一度きり**の用途に限る。継続実行では課金分が積み上がる。

## 守る不変条件
- 1 ホストあたりのアクセス間隔（delay と robots.txt の Crawl-delay）は、並列化しても絶対に縮めない。
  ホストロックがこれを機械的に担保する。
- robots.txt 不許可・取得不能は今と同じく「巡回しない」。
- 取得した生 HTML はコミットしない（ADR 0002）。並列でも変わらない。

## 影響
- `PoliteClient` にロックを足すだけで、逐次利用の互換性は保たれる。呼び出し側は Executor で包む。
- akiya-atlas / japan-life-checklist など全サービスの発見・巡回が速くなる。
- 計測（`request_count`・所要時間）はロック下で正しく集計する。
