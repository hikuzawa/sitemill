# ADR 0019: ASP 案件の選定を明文化した物差しで行う

- ステータス: 採用（2026-09-12）。除外 3「地域が合わない」は ADR 0021 で保留に変更した（除外は信頼性・導線・しきい値の 3 つ）

## 背景
ASP の検索結果を眺めて提携先を選ぶ作業は、毎回同じことを頭の中でやり直している。
報酬額が目に入りやすく、成果条件の重さや確定率のように後から効く条件が軽く扱われやすい。
一方で「これは載せない」という線（情報商材・投資勧誘）は毎回同じなのに、判断の記録が残らない。

選定そのものは自動化できないが、**判断の材料を揃えて並べるところまで**は決定的にできる。
どのサービスでも同じ手順になるので engine に置く。何を良しとするかはサービスごとに違うので、
物差し（プロファイル）は外から渡す。

提携申請そのものは人が行う。このツールは「どれに、どの順で申請するか」を決める材料までを作る。

## 決定

### 貼り付けたテキストを決定的に構造化する（`sitemill/affiliate/parse.py`）
ASP の画面は取得の対象にしない（ログインが要る、robots の対象、規約もある）。
人が検索結果をコピーして貼るだけにする。貼ったテキストからは LLM を使わずに読み取る。

- ラベルの異名表（`成果報酬` / `報酬額` / `成果条件` / `確定率` / `EPC` / `再訪問期間` / `提携` …）だけを持ち、
  値は `parse/jp` の決定的パーサで数値にする（quote-then-parse、ADR 0004）。
  同じテキストを貼れば必ず同じ表が出る
- 読めなかった項目は `None` のままにして「不明」と出す。**推定で埋めない**。
  不明が多い案件は表の末尾に「読めなかった項目」として並べ、貼り直しの手がかりにする
- 案件の切れ目は、空行、または「ラベル付きの行が続いたあとに現れたラベルの無い行」で決める。
  ラベルらしく見えても値が項目の形（金額・％・日数）になっていなければラベルとして扱わない
  （「提携先の会社」の「提携」を提携状況のラベルにしないため）

### 判定は 2 段にする（`sitemill/affiliate/screen.py`）
まず落とすものを落とし、残ったものに点をつける。落とす理由と点の内訳は必ず文章で残す。

**除外**（1 つでも当たれば不採用。上から順に見て、最初に当たった理由をそのまま出力に出す）

1. **サイトの信頼性を損なう**: プロファイルの `exclusions` に当たる。
   情報商材・スクール・投資勧誘・費用が先に出るものを既定で置く。
   空き家の所有者に「相談先」として案内する枠なので、ここが崩れると枠ごと意味を失う
2. **導線に合わない**: どの `funnels` にも当てはまらない。
   置く場所が無い案件は、報酬がいくら高くても掲載できない
3. **地域が合わない**: 成果の出る地域がサイトの対象地域と重ならない。
   長野県中心のサイトで首都圏限定の案件を出しても、押されて終わる
4. **しきい値を割る**: 確定率・EPC・報酬が下限未満。
   **記載が無いものは落とさない**（不明を「低い」と読み替えない）

**点**（満点 100。内訳は `weights`）

| 軸 | 既定 | 考え方 |
| --- | --- | --- |
| 導線適合 | 40 | 案件名に導線の語があれば満点。成果条件・広告主名だけなら 0.7、掲載文の隅にあるだけなら 0.5 |
| 成果条件の重さ | 25 | 軽い（無料見積・資料請求で成果）ほど高い。面談・契約まで必要なものほど低い |
| 確定率 | 20 | 下限から 100% までを線形に割り当てる |
| 稼ぎ | 15 | EPC があれば EPC、無ければ報酬額。EPC は成果条件と確定率を織り込んだ実績値なので優先する |

報酬額を主軸にしないのが要点。報酬 15,000 円・確定率 20%・成約が条件の案件より、
報酬 8,000 円・確定率 82%・申込が条件の案件のほうが実入りも所有者の役にも立つ。

**保留**。除外に当たらないが点が `min_score` に届かないものは、除外せず「保留」にする。
落とす理由はないが今すぐ申請する理由もない、という状態を表に残す。後から見直せる。

**並び順**。申請 → 保留 → 除外。同じ点なら**審査のある案件を先**に出す。承認に日数がかかるので、
先に出しておくほど早く掲載できる。

### 物差しはサービス側に置く（`sitemill/affiliate/profile.py`）
どの導線を持つか・どの地域で成果が出るか・何を載せないかはサービス固有なので、engine は持たない。
YAML で渡す。重みとしきい値も同じ YAML に書き、**engine の中に数字を隠さない**。
判定が気に入らなければコードではなくプロファイルを直す。

雛形は `profiles/akiya-owner.example.yaml`（空き家所有者向け導線）。
サービスのリポジトリに `data/affiliates/profile.yaml` として置いて使う。

### 承認後は同じデータから掲載側の様式に変換する（`sitemill/affiliate/emit.py`）
選定に使った構造化データをそのまま掲載側の様式にする。手で書き写す工程を挟まないので、
表に出ていた値とコードの値がずれない。

様式もサービスごとに違う（掲載側のデータ構造が違う）ので、engine は雛形を持たない。
プロファイルの `emit.handoff`（受け渡し用の YAML）と `emit.code`（登録用のコード片）に書いた
`{...}` を埋めるだけにする。契約後にしか分からない項目（計測 URL・飛び先の制約）は雛形で空にし、
**空のまま出す**。ダミーを入れない（akiya-atlas ADR 0010 の「契約が済むまで準備中」と同じ扱い）。

## 使い方

```bash
# 1. ASP の検索結果をコピーしてテキストに貼る（案件の間に空行があると確実に分かれる）
# 2. 判定する
uv run sitemill offers screen --profile data/affiliates/profile.yaml \
  --input paste.txt --asp a8 --out report.md --json data/affiliates/screened.json

# 3. report.md の表を見て申請する（申請そのものは人が行う）
# 4. 承認されたら、選定に使ったのと同じデータから掲載側の様式に変換する
uv run sitemill offers emit 解体工事110番 --json data/affiliates/screened.json \
  --profile data/affiliates/profile.yaml --offer-id kaitai-110
```

## 却下した案

- **ASP の管理画面を巡回して案件を取る**: ログインが要るうえ規約の対象になる。
  貼り付けなら人が見た画面そのものが入力になり、取り違えも起きない
- **LLM に案件を読ませて点をつけさせる**: 数値を LLM に決めさせない原則（ADR 0004）に反する。
  同じ入力で違う順位が出ると、判定基準を直したのか LLM が揺れたのかが分からなくなる
- **報酬額の高い順に並べるだけ**: 確定率と成果条件を無視した順位になる。
  高額・低確定率・成約条件の案件が常に先頭に来る
- **除外した案件を出力から消す**: なぜ選ばなかったかが残らず、次に同じ案件を見たときに同じ検討を繰り返す

## 影響
- `sitemill/affiliate/` を追加。既存の処理には触らないので後方互換
- `sitemill/parse/jp/numbers.py` に `parse_percent` を追加（確定率・料率の読み取り）
- CLI に `sitemill offers screen|emit` を追加。site.toml を必要としない（サービスのルート以外でも動く）
