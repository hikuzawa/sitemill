# ADR 0028: 鮮度は「出どころのページを最後に読めた時刻」で進める

- ステータス: 採用（2026-09-29）

## 背景

同じ考え方を 3 か所で別々に持っていて、片方だけ直る事故が起きた（akiya-atlas の設計案 L）。

- japan-open-today の施設: 鮮度を抽出した時刻で測っていた。抽出は中身が変わったページにしか走らない
  ので、最初の抽出（9/12〜14）から 14 日たった 9/27〜28 に、毎日読めている施設まで「取得が 14 日以上
  できていない」に落ち、本番の判定が「開いている 8・不明 152」になった（2026-09-28 に直した）
- akiya-atlas の補助制度: 確認日が抽出した日のままで、2,638 件が 2027-03-14〜15 に一斉に「情報が古い
  可能性」になるところだった（2026-09-28 に直した）
- akiya-atlas の物件: `last_seen_at` を別の形で進めていた

## 決定

`sitemill.diff.freshness` に置く。サービスは「どのレコードがどのページから来たか」と「どの項目を
進めるか」だけを渡す。

- `page_read_at(url_state)`: そのページを最後に読めた時刻。次の 3 つがそろわなければ None
  1. 失敗が無い（`error` が空）
  2. 読めた時刻がある（`fetched_at`。200 でも 304 でも進み、失敗では進まない）
  3. 抽出したときから中身が変わっていない（`content_hash == extracted_hash`）
- `read_at(state, urls)`: 出どころのページを**すべて**読めているとき、いちばん古く読めた時刻。読むだけ。
  データを読むたびに鮮度を計算するサービス（japan-open-today）が使う
- `mark_read(records, state, source_url=..., field=..., as_date=...)`: レコードの項目を読めた時刻まで
  進め、進めた件数を返す。前に戻さない。日付で持つ項目は JST の日付にする。項目を保存して持つ
  サービス（akiya-atlas の物件・補助制度）が使う

3 つ目の条件は、japan-open-today の最初の直し（2026-09-28）には無かった。中身が変わったのに抽出が
まだ・失敗した晩（LLM の障害など）に、古い事実を新しいものとして扱う穴になる。切り替えた時点で該当する
ページは 0 件だった（毎晩、巡回の直後に抽出している）。

## 影響

- japan-open-today は v0.7.13 で `read_at` に切り替えた。切り替えの前後で、8 日分の判定の内訳・
  281 施設それぞれの判定（時刻・根拠を含む）・鮮度の時刻がすべて一致した
- akiya-atlas の物件と補助制度の切り替えは、akiya-atlas のセッションが行う
- 古い事実が表示に出るのは正しい（取得の失敗・中身が変わって抽出していない・巡回先から外した）。
  それで「不明」が急に増えたら、公開前の歯止め（ADR 0026）が配置を止める
