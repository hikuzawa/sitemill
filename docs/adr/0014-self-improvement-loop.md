# 0014. 自動改善ループ（設計のみ。実装は着手条件を満たしてから）

状態: 提案（2026-09-11）。実装は未着手。着手条件は §6。

## 背景

全国 1,741 市町村へ広げる過程で、誤りは人手ではなく仕組みで直してきた（ADR 0011 の発見・分類、
0012 の公開前チェック、0013 の並列巡回、akiya-atlas ADR 0008 の自己修復）。実際に効いた直しは、
いずれも「計測 → 原因の切り分け → 小さな規則の追加 → 回帰テストで固定」という同じ形をしている。

この形は繰り返しが多く、1 件ずつ人間が回すには時間がかかる。一方で、全部を LLM に任せると
何をどう変えたのか追えなくなり、ライセンスや個人情報の規則まで書き換わる危険がある。
そこで **どこまでを自動でやるか** を先に決める。

## 1. 決定: 分析はコード、判断は LLM

| 役割 | 担当 | 例 |
| --- | --- | --- |
| 計測 | コード | 抽出メトリクス（ADR 0010）、0 件の source、eval の正答率、費用とトークン |
| 切り分け | コード | 「本文が空」「引用が原文に無い」「分類は一覧だが 0 件」などの分類 |
| 仮説と修正案 | LLM | プロンプトの言い回し、抽出仕様に足す語、しきい値の候補 |
| 適用の可否 | コード | 許可された変更範囲か、eval が劣化しないか |
| 記録 | コード | 変更前後の差分・計測値を `data/runs/` に残す |

LLM に「数値を直接決めさせない」点は quote-then-parse（ADR 0004）と同じ考え方で、
**証拠（計測結果）を作るのはコード、証拠の読み方を提案するのが LLM**とする。

## 2. 決定: 処理ごとにモデルを指定する

`site.toml` の `[llm]` を処理別に持てるようにする（既定は現在の 1 モデル）。

```toml
[llm]
provider = "anthropic"
model = "claude-haiku-4-5"      # 既定（抽出）

[llm.tasks]
extract = "claude-haiku-4-5"    # 量が多い。安く速く
diagnose = "claude-opus-5"      # 数が少なく、難しい判断
propose  = "claude-opus-5"      # 修正案の作成
```

理由: 抽出は 1 日数百回走るので単価が効く。診断と提案は 1 日数回なので、賢い方が結果的に安い。
実測（2026-09-11 の全国バックフィル）では抽出 271 回で約 $4.8、診断に相当する処理は 0 回だった。

## 3. 決定: 変更してよい範囲を限定する

自動で変えてよいもの（許可リスト方式。ここに無いものは変えない）:

- 抽出プロンプト（`prompts/*.md`）の本文
- 抽出仕様の語彙（除外語・同義語。例: 価格として扱わない語）
- 分類のしきい値と重み（`classify/listing_score.py` の定数）
- 発見の候補選択の重み（アンカー語の点数）

自動で変えてはいけないもの:

- スキーマ（`schema.py`）と出力の形
- ライセンス判定（ADR 0005）と巡回の礼儀（ADR 0003）
- 個人情報の規則（ADR 0012）と要約の方針（写真・本文を載せない）
- テンプレートと公開ページの文言
- CI・デプロイの設定

## 4. 決定: 1 回 1 件、必ず戻せる形にする

- 1 回の実行で変更するのは **1 件だけ**。まとめて直すと、どれが効いたか分からない。
- 変更は必ずブランチとコミットにする（`improve/<日付>-<対象>`）。
- 適用前後で `sitemill eval` を回し、**正答率が下がったら自動で `git revert`**（`data/runs/improve-*.json` に理由を残す）。
- 変わらない場合も戻す。改善が確認できたときだけ残す。
- 人間は PR を見るだけでよい形にする（マージは人間が行う）。

## 5. 決定: 何を入力にするか

毎日のパイプラインが残す計測だけを入力にする。相手サイトを追加で叩かない。

- `data/runs/latest-extract.json` の項目別の `parsed / unparsed / not_found / quote_not_in_source`
- `sitemill eval` の fixture ごとの差分
- 0 件が続く source の一覧（`heal` の報告）
- 費用（入出力トークン）

## 6. 着手条件

次をすべて満たすまで実装しない。

1. 日次パイプラインが **2 週間** 失敗 Issue なしで回っていること
2. `eval` の fixture が主要な型（表形式・カード形式・詳細ページ）を **各 3 件以上** 含むこと
3. 1 か月の LLM 費用の上限を決め、実測がその半分以下であること
4. 変更範囲の許可リスト（§3）がコードの定数として書かれ、テストで守られていること

## 7. 代替案と却下の理由

- **全部 LLM に任せる**: 何が変わったか追えず、ライセンスや個人情報の規則まで触る危険がある。却下。
- **人間が毎回直す**: 今のやり方。件数が増えると追いつかない。自動化の対象にする。
- **強化学習のように指標だけで自動調整**: 指標が上がっても、公開してよい内容かは別問題。
  公開前チェック（ADR 0012）を通らない変更が生まれる。却下。
